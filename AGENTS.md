# Работа агента в проекте

## Общие условия

- Отвечай на русском; комментарии в коде — на русском, если задача не требует иного. Идентификаторы и имена файлов — на английском.
- Проект использует собственную архитектуру. Не заменяй её FSD или другой методологией без явной задачи.
- Архитектурные документы обязательны для человека и агента в пределах затронутой задачи. Этот файл задаёт порядок работы, а не вторую версию архитектуры.

## Что читать перед изменением

Перед изменением кода прочитай [краткую структуру](docs/ProjectStructure.md) и [Code Style Guide](docs/CODE_STYLE_GUIDE.md). Затем выбери дополнительные разделы по задаче; для задачи нескольких типов прочитай их объединение.

| Задача | Дополнительное чтение |
|---|---|
| Новый проект, выбор зависимостей или настройка UI-инструментов | [React-профиль](docs/ReactPreferences.md), существующие package scripts и конфигурации; [скелет проекта](examples/react-reference/README.md) как ориентир раскладки и оформления |
| Страница или локальные компоненты | [app](docs/ProjectStructure.full.md#app---точка-входа-приложения) |
| Новый компонент или изменение его ответственности | [components](docs/ProjectStructure.full.md#components---компоненты-приложения), включая границы UI, layouts, patterns и features |
| Загрузка, сохранение, формы, DTO, состояние | [services](docs/ProjectStructure.full.md#services---работа-с-side-эффектами), [DTO и модели](docs/ProjectStructure.full.md#dto-vs-внутренние-модели), [store](docs/ProjectStructure.full.md#store---клиентское-состояние) |
| Создание/перенос файлов, изменение импортов/экспортов | [размещение](docs/ProjectStructure.md#правило-каждый-домен--отдельная-папка), [публичный API](docs/ProjectStructure.md#дерево-публичных-экспортов), [зависимости](docs/ProjectStructure.md#dependency-rules--карта-допустимых-зависимостей), [имена файлов](docs/CODE_STYLE_GUIDE.md#file-naming-convention) |
| Утилита или общий хук | [lib](docs/ProjectStructure.full.md#lib---утилиты-и-вспомогательные-функции), [модуль утилиты](docs/ProjectStructure.md#модуль-утилиты) |
| Тесты, моки, stories | [mocks](docs/ProjectStructure.full.md#mocks---моковые-данные-для-тестов-и-разработки), [Storybook](docs/ProjectStructure.full.md#storybook) |
| Первое изменение в приложении | [Паспорт и команды](README.md#применение-в-конкретном-проекте), [сквозной пример](docs/ProjectStructure.full.md#сквозной-пример-редактирование-карточки) |
| Завершение изменения кода | [Критерии готовности и проверки](docs/ProjectStructure.full.md#готовность-изменения-и-проверки) |
| Только документация | Изменяемый раздел, его основной источник и связанные ссылки/краткие пересказы; прочие разделы кода читать не требуется |

Полную структуру не нужно каждый раз читать целиком. Уже прочитанный актуальный раздел в рамках текущей работы можно использовать повторно; после его изменения перечитай затронутое правило. Ссылки — маршрут к обязательным правилам, а не замена чтению.

## Особенности, которые легко потерять

- [Atoms](docs/ProjectStructure.full.md#atoms---примитивы-стили-и-токены) — стили и классы, без production React-обёрток ради variant.
- [DTO-преобразования](docs/ProjectStructure.full.md#dto-vs-внутренние-модели) принадлежат сценарию-потребителю; совпадение кода разных страниц не требует объединения.
- [Services и store](docs/ProjectStructure.full.md#server-state-и-внутреннее-состояние) не подключают друг друга; внутреннюю модель передаёт владелец сценария.
- [Дерево публичных экспортов](docs/ProjectStructure.md#дерево-публичных-экспортов) не отменяет границы слоёв. Полный контракт находится по ссылке.

## Порядок работы

1. Определи область задачи. Посмотри состояние Git, существующую реализацию, потребителей и подходящие примеры; не перезаписывай чужие незакоммиченные изменения.
2. Прочитай документы по таблице. До создания файла выбери владельца модуля, допустимые зависимости и публичный API.
3. При первоначальной реализации согласуй набор инструментов по ReactPreferences один раз. Проверь актуальные стабильные версии и совместимость по его разделу «Актуальность версий»; не копируй номера зависимостей из примера без проверки. Не подменяй подходящие библиотеки самописной инфраструктурой и не добавляй тестовый framework автоматически. Внеси изменения в пределах задачи. При переносе или изменении API проверь потребителей и импорты.
4. Запусти проверки, соответствующие изменению и реально доступные в проекте. Ориентируйся на [критерии готовности](docs/ProjectStructure.full.md#готовность-изменения-и-проверки). Команды бери из README, package scripts и конфигурации; не выдумывай отсутствующие команды. Для документации проверь ссылки и diff.
5. Если изменён архитектурный контракт, обнови основной раздел, связанные примеры и краткие пересказы.
6. В результате сообщи, что изменено, что проверено и какие проверки не удалось выполнить. Не представляй непроведённые проверки как успешные.

## Исключения и противоречия

[Распределение ответственности документов](README.md#документация) определяет, где находится основной текст каждого правила. Краткая карта и примеры не вводят дополнительные требования вместо него.

Применяй описанные исключения только в указанной области. Не выводи новое исключение из случайного примера или существующего нарушения в коде. Если противоречие влияет на реализацию, укажи конкретные места и уточни решение; независимую часть задачи можно продолжать.
