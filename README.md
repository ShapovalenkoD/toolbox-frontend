# toolbox-frontend

Соглашения об организации frontend-проектов: архитектура, границы ответственности и стиль кода. **Профиль — конкретно React и TypeScript**, включая React-based meta-framework (Next.js). Для другого UI-фреймворка или библиотеки — Vue/Nuxt, Angular, Svelte, SolidJS и т.п. — эти правила не адаптируются: такой проект живёт по собственным принятым правилам, а вопрос переноса обсуждается отдельно.

## Документация

Правила архитектуры и стиля общие для разработчиков и агентов. У каждой темы есть основной документ; остальные могут содержать краткий пересказ со ссылкой.

| Документ | Ответственность |
|---|---|
| [AGENTS.md](AGENTS.md) | Порядок работы агента, маршрут чтения по задачам, проверки и работа с противоречиями |
| [ProjectStructure.md](docs/ProjectStructure.md) | Карта каталогов, размещение модулей, публичный API и допустимые зависимости |
| [ProjectStructure.full.md](docs/ProjectStructure.full.md) | Контракты слоёв, поток данных, сквозной пример, критерии готовности, моки и stories |
| [CODE_STYLE_GUIDE.md](docs/CODE_STYLE_GUIDE.md) | Именование файлов и идентификаторов, интерфейсы, экспорт и соглашения о написании кода |
| [ReactPreferences.md](docs/ReactPreferences.md) | Предпочтительные инструменты, выбор стека, обязательный Storybook и порядок первой итерации |
| Этот README | Точка входа для человека и навигация; сведения о запуске конкретного проекта добавляются при его настройке |

[React reference](examples/react-reference/README.md) — скелет нового проекта: образцы файлов формы, DTO-преобразований, сервиса, UI-кита, утилит и stories, плюс biome.json. Без package.json и зависимостей; служит образцом раскладки и оформления и удаляется после переноса структуры.

### Как читать разработчику

Начни с краткой структуры и Code Style Guide. Затем открывай раздел полной версии, относящийся к задаче. Для выбора UI/business-компонента используй [сравнение organisms, patterns и features](docs/ProjectStructure.full.md#граница-organisms-patterns-и-features), для работы с внешними данными — [DTO и внутренние модели](docs/ProjectStructure.full.md#dto-vs-внутренние-модели).

Маршрут для агента находится в корневом AGENTS.md. В инструменте, который не обнаруживает этот файл автоматически, его нужно явно подключить как инструкцию проекта.

### Как поддерживать правила

Изменяй основной раздел темы, затем связанные примеры и краткие пересказы. Пересказ не должен создавать отдельную версию правила; при расхождении его приводят в соответствие основному контракту. Противоречия между основными контрактами требуют явного решения.

Предпочтения и обязательные инструменты React-профиля определены в [ReactPreferences](docs/ReactPreferences.md). Они не требуют установки всех перечисленных библиотек в каждое приложение. Там, где предложены варианты, выбранный вариант и версии фиксируются в документации проекта. Реальный паспорт запуска и команд проверок оформляется отдельно при настройке проекта; команды-заглушки не считаются рабочими.

## Применение в конкретном проекте

Этот репозиторий содержит соглашения и скелет проекта в examples/react-reference. Корневого package.json и настроенного набора команд запуска/проверок сейчас нет.

При переносе соглашений в приложение заполните паспорт ниже по фактическим конфигурациям и доступным scripts. Не устанавливайте зависимости и не выбирайте стек только для заполнения документации.

### Паспорт проекта

| Поле | Что зафиксировать в приложении |
|---|---|
| Назначение | Пользовательская задача приложения и основные сценарии |
| Среда | Версии runtime, package manager и источник фиксации версий |
| UI и выполнение | Framework, версия, SPA/SSR/другой режим |
| Routing | Выбранный подход и местоположение конфигурации |
| Состояние и внешние данные | Store, query-инструмент либо обычные сервисные методы |
| API | Источник контракта, ручная реализация/codegen, команда генерации при наличии |
| Стили и UI-документация | Подход к CSS и Storybook; исключение требует явного решения владельца, причины и альтернативы проверки UI |
| Тесты | Используемые инструменты и расположение тестов |
| Окружение | Обязательные переменные, безопасный пример env, способ получения dev-доступа без секретов в документации |
| Зависимые сервисы | Что должно быть запущено для локального сценария и есть ли режим с моками |
| Первый сценарий | Какой экран открыть и какой результат означает успешный запуск |

### Команды проекта

Все значения ниже пока **не заполнены**: они относятся к будущему приложению. После заполнения команда должна работать из указанного каталога.

| Операция | Точная команда и рабочий каталог |
|---|---|
| Установка зависимостей | Не задано |
| Запуск dev-среды | Не задано |
| Проверка типов | Не задано |
| Lint и форматирование | Не задано |
| Тесты | Не задано |
| Production-сборка | Не задано |
| Stories | Не задано / явно оговорённое исключение |
| Генерация API | Не задано / не используется |

Если проверка не настроена, явно укажите это. Отсутствие команды не означает успешное прохождение проверки. Различайте локальные проверки и реально выполняемые проверки CI.

### Первое изменение

1. Ознакомьтесь с краткой структурой и стилем, затем с разделами по своему сценарию.
2. Подготовьте окружение и выполните команды из заполненного паспорта.
3. Пройдите первый пользовательский сценарий; при невозможности запуска зафиксируйте причину.
4. Найдите владельца нужного поведения и его публичные зависимости. Для формы ориентир — [сквозной пример](docs/ProjectStructure.full.md#сквозной-пример-редактирование-карточки).
5. Внесите небольшое изменение и проверьте его по [критериям готовности](docs/ProjectStructure.full.md#готовность-изменения-и-проверки).

Документация описывает целевую организацию приложения. Наличие схемы каталогов не означает, что каждый каталог или инструмент уже создан в этом репозитории.

### Начало работы в новой сессии

1. Разместите AGENTS.md в корне репозитория приложения, а документы соглашений, включая ReactPreferences.md, — в docs/, сохранив относительные ссылки. Если в приложении уже есть правила, сначала согласуйте их; не перезаписывайте существующие инструкции автоматически.
2. В README приложения добавьте навигацию и заполненный паспорт проекта. Сохраните разделы и якоря, на которые ссылаются соглашения. Описание текущего toolbox-репозитория и незаполненные команды не копируйте как факты о приложении.
3. Откройте новую задачу в каталоге приложения. Для инструмента, который сам не читает AGENTS.md, явно укажите его в стартовом запросе.
4. Передайте полное условие задания, материалы, ограничения стека и критерии приёмки. Новая сессия не должна восстанавливать решения из истории этой переписки: источником служат файлы проекта.
5. Согласуйте компактный выбор инструментов по ReactPreferences; уже принятые решения повторно согласовывать не нужно. Начните с одного законченного сценария. До реализации определите владельцев данных, преобразований и операций; затем проверьте сценарий доступными командами и вручную. Неопределённые требования задания уточняются, а различия с общими соглашениями фиксируются явно.

Если новая задача — только подготовка структуры или обсуждение задания, не создавайте приложение и не устанавливайте зависимости без этой цели.
