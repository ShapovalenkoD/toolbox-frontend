# Структура проекта - полная версия

> Основной документ для контрактов слоёв, потоков данных и подробных примеров. Карта, публичный API и матрица зависимостей: [краткая структура](ProjectStructure.md). [Роли документов](../README.md#документация).

Деревья ниже показывают существенные для раздела файлы, а не полный scaffold: группирующие индексы, тесты и обязательные stories могут быть опущены для краткости. При реализации они добавляются по основным правилам. Ненужные пустые файлы не создаются.

## `docs` - Документация проекта

Находится в корне проекта (рядом с `package.json`), **не** внутри `src/`.

- **Содержит**: общую документацию для разработчиков и агентов. Порядок работы агента находится в корневом [AGENTS.md](../AGENTS.md); отдельной копии инструкций внутри docs нет.

## `app` - Точка входа приложения

- **Содержит**: корневую композицию и провайдеры (store, router, theme).
- **Не содержит**: конфигурацию store (она в store/) и модули страниц при свободной структуре проекта.
- Страницы размещаем в src/pages/, настройку маршрутизации — в src/routes/ при её наличии. Next.js и другие framework с обязательными файловыми соглашениями имеют приоритет.
- Страница — модуль: локальные компоненты в _components/, интерфейсы в PageName.interface.ts рядом со страницей, утилиты — в её utils/. Не создаём types/ только потому, что интерфейс используют несколько файлов страницы.
- Страница вызывает services, преобразует и объединяет DTO, передаёт внутренние модели в store. Короткая логика остаётся непосредственно в компоненте; companion-хук выделяется только при самостоятельной ответственности.
- Переиспользуемый целиком сценарий переносится в business pattern или feature вместе с поведением и преобразованиями.

~~~text
src/
  app/
    App.tsx
    RootProvider.tsx
  pages/
    profilePage/
      index.ts
      ProfilePage.tsx
      ProfilePage.interface.ts
      _components/
        cardProfile/
          index.ts
          CardProfile.tsx
          CardProfile.interface.ts
          cardProfile.module.css
~~~

RootProvider объединяет провайдеры приложения и не содержит бизнес-логики.

### Routing

- **Config-based**: конфигурация в src/routes/router.tsx; страницы импортируются через pages API.
- **File-based**: имена и сегменты определяет выбранный router/framework. Не создаём второй параллельный механизм маршрутов.
- **Lazy loading**: используем механизм выбранного router/framework.
- **Guards**: в routes/guards/ либо средствами framework; проверка UI не заменяет авторизацию на сервере.
- Для одного экрана без маршрутизации папку routes и библиотеку router не создаём.

## `assets` - Статические ресурсы

В примере используется корневая папка assets; фактическое расположение зависит от выбранного сборщика.

- **Примечание**: `assets/` — условное имя в примерах. Папка ресурсов, раздаваемых напрямую, и импортируемые сборщиком ресурсы могут иметь разные пути и обработку. Их фактические пути (`public/`, `src/assets/` и т.п.) фиксируются в паспорте проекта; не переименовывай их без настройки инструмента.
- **Содержит**: изображения, шрифты, SVG-иконки, видео и другие файлы, которые не являются кодом.
- **Пример структуры**:

  ```
  assets/
    ├── images/
    │   ├── logo.svg
    │   └── hero-banner.webp
    ├── fonts/
    │   └── Inter-Regular.woff2
    └── icons/
        ├── arrow-right.svg
        └── close.svg
  ```

- **Правила**:
  - Именование: `kebab-case`
  - Статические SVG-иконки остаются ресурсами; их визуальные классы могут находиться в `components/ui/atoms/icons/`. Пустую React-обёртку ради применения стилей не создаём. Композиция иконки с поведением или другими примитивами относится к molecules.
  - SVG-иконки, используемые как файлы (background, img src) → `assets/icons/`

## `components` - Компоненты приложения

- **Дизайн-система**: ссылка задаётся в паспорте конкретного проекта, если источник дизайна есть.

  ```
  components/
    ├── ui/                      # UI-кит (без бизнес-логики)
    └── business/                # Прикладные сценарии и композиция проекта
  ```

### `ui/` - UI-кит

- **Правило**: не импортирует из `services/`, `store/`, `components/business/` или `app/`, `pages/`, `routes/`, включая DTO-типы. Не получает через props операции доступа к внешним данным. Может сообщать о действиях пользователя через callbacks и получать loading/error как входное состояние.

#### `foundation/` - Базовые стили

- **Правила**:
  - Разделяем файлы по назначению: colors.css, typography.css, tokens.css, reset.css, base.css. index.css задаёт порядок их подключения; пустые файлы не создаём.
  - Базовые классы, определения темы и переменных, утилитарных классов
  - Слой содержит: базовые стили (reset/normalize), тему, палитру, типографику, интервалы и глобальные токены. Стили конкретного button/input принадлежат atoms и используют foundation.
- **Пример**:

  ```
  export const Palette = {
    primary: '#0ea5e9',
  } as const;

  export type PaletteKey = keyof typeof Palette;
  ```

#### `atoms/` - Примитивы (стили и токены)

- **Правила**:
  - Атомы — это **стили, глобальные CSS-классы и токены**, а не React-компоненты. Используем button.css с классами button, button-size-lg, button-variant-primary; CSS Modules оставляем локальным композициям.
  - Общий ui/index.css подключает foundation, затем atoms в приложении и Storybook. CSS-only каталоги не требуют TS-индексов.
  - Варианты, размеры и состояния визуальных примитивов: button, link, input, label. Компонентные стилевые токены используют глобальные токены foundation.
  - React-компонентов и обращений к данным здесь нет. Пустые Button/Input-обёртки ради передачи variant не создаём.
  - Класс button можно применить к ссылке, класс link — к кнопке. Семантику HTML, клавиатурное поведение и корректность disabled обеспечивает потребитель, а не CSS.
  - Stories атомов демонстрируют классы на HTML-элементах; демонстрационный JSX не превращает атом в production-компонент.
  - Каждый атом обязан иметь **story** по [правилам визуальной документации](#storybook).
- **Пример структуры**:
  ```
  atoms/
    ├── button/
    │   ├── button.css         # Стили кнопки
    │   ├── button.styles.ts          # Программные стили (если нужны)
    │   └── Button.stories.tsx        # Storybook story
    ├── input/
    │   ├── input.css
    │   └── Input.stories.tsx
    └── icons/
        ├── icons.css
        └── Icons.stories.tsx
  ```

#### `molecules/` - Простые композиции

- **Правила**:
  - Внутреннее состояние допускается
  - Небольшая законченная группа примитивов либо примитив с нетривиальным UI-поведением. Пустая обёртка для variant сюда также не нужна.
  - TextField объединяет label, input и сообщение об ошибке, связывает подпись и поле. LoadingButton объединяет оформление кнопки и индикатор; состояние загрузки получает снаружи.
  - Не выполняют получение или сохранение прикладных данных.
- **Пример структуры**:
  ```
  molecules/
    ├── radioGroup/
    │   ├── index.ts
    │   ├── RadioGroup.tsx
    │   ├── RadioGroup.interface.ts
    │   └── radioGroup.module.css
    ├── loadingButton/
    │   ├── index.ts
    │   ├── LoadingButton.tsx
    │   ├── LoadingButton.interface.ts
    │   └── loadingButton.module.css
    └── alert/
        ├── index.ts
        └── Alert.tsx
  ```

#### `organisms/` - Сложные блоки

- **Правила**:
  - Сложная UI-композиция и взаимодействие нескольких частей: Table с сортировкой/выделением, Pagination с вычислением видимых страниц, carousel.
  - Pagination получает общее число элементов, размер и текущую страницу; вычисляет число страниц, окно соседних номеров, многоточия, переходы назад/вперёд и к крайним страницам. Например, для 1000 элементов по 100 на странице и текущей страницы 4: `← 1 … 3 4 5 … 10 →`.
  - Это логика UI: Pagination сообщает выбранную страницу через `onPageChange`, но не загружает данные. Наличие вычислений и переменного количества кнопок не делает её business pattern.
  - Для Pagination предусматриваются пустой результат, одна страница, границы диапазона и изменение общего количества элементов; номер страницы должен оставаться допустимым.
  - Organism получает данные и состояние операций извне, сообщает о UI-событиях. Не вызывает переданные load/save-операции и не управляет их выполнением.
  - Количество элементов — вспомогательный признак сложности, не критерий отделения от бизнеса.
  - Допускается использование сторонних UI-библиотек (слайдеры, графики и т.д.)
- **Пример структуры**:
  ```
  organisms/
    └── carousel/
        ├── index.ts
        ├── Carousel.tsx
        ├── Carousel.hooks.ts
        ├── Carousel.interface.ts
        └── carousel.module.css
  ```

### `business/` - Бизнес-компоненты

Слой включает прикладные сценарии и специфичную для проекта организацию интерфейса. Принадлежность к business не требует наличия бизнес-логики: layouts знают структуру областей приложения и отвечают только за их расположение.

- **Правило**: прямое подключение services/store разрешено features. Patterns получают операции через props; layouts отвечают только за композицию. Категория определяется ответственностью, а не обязательным наличием импорта.

#### `layouts/` - Композиции макетов

- **Правила**:
  - Отвечают за расположение переданного содержимого: области, размеры, отступы и адаптивное поведение.
  - Находятся в business, поскольку отражают композицию конкретного приложения. Переносимость между проектами — ориентир; основной критерий — знание структуры приложения.
  - Не выбирают данные и не управляют загрузкой, сохранением, проверкой формы или другими прикладными операциями. Не подключают services/store.
  - Могут принимать через props/children интерактивные компоненты, не управляя их поведением.
  - Переиспользуются в pages/features/patterns, когда повторяется структура расположения; отдельный layout для каждой страницы не обязателен.
  - Универсальные Stack/Grid, задающие выравнивание и интервалы без знания структуры приложения, относятся к UI.

**Пример:** PageLayout размещает breadcrumbs, заголовок, основную область и боковую панель. Страница передаёт содержимое этих областей. Pagination вычисляет навигацию — это UI-organism; DataGrid управляет загрузкой — это business pattern. Наличие или отсутствие интерактивности само по себе не отделяет layout от UI: статичный badge тоже UI-компонент.
- **Пример структуры**:
  ```
  layouts/
    ├── main/
    │   ├── index.ts
    │   ├── MainLayout.tsx
    │   └── CardLayout.tsx
    └── card/
        └── product/
            ├── index.ts
            ├── ProductCardLayout.tsx
            └── productCardLayout.module.css
  ```

#### `patterns/` - Настраиваемые бизнес-сценарии

- Управляют повторяемым прикладным процессом: редактированием, проверкой, сохранением и обработкой результата.
- Получают данные, схемы проверки и операции через props. Могут вызвать переданную операцию, ожидать результат и обрабатывать loading/error/success.
- Не импортируют исполняемый код из `services/` и `store/`, в том числе косвенно через общие хуки. Не получают эти зависимости из глобального context.
- Импорт типов DTO из `services/` разрешён только для явного контракта переданных данных/операций и локальных конвертеров. Это не подключает реализацию сервиса.
- Не принимают функции-хуки через props: передаются обычные callbacks или уже полученные значения.
- Конвертеры принадлежат pattern, если именно он владеет переиспользуемым сценарием. Конкретное преобразование отдельной страницы остаётся на странице.
- Иконки, render-функции и количество props сами по себе не определяют принадлежность к patterns.

Основной пример: **DataGrid** объединяет UI-organisms Table и Pagination и управляет загрузкой через обычную функцию `loadData`, полученную из props. Конкретный сервис он не импортирует.

- При смене страницы, размера страницы или сортировки DataGrid формирует параметры и вызывает `loadData`.
- Управляет состояниями loading/error/empty/success и передаёт строки в Table, общее количество элементов и текущую страницу — в Pagination.
- При нескольких запросах результат устаревшего запроса не должен заменять актуальный; конкретный механизм отмены или игнорирования зависит от реализации.
- `loadData` — операция с результатом, а не функция-хук. Её реализацию передаёт страница или feature. Даже при использовании React Query/SWR для этого режима нужен обычный async-метод сервиса или callback поверх императивного query API; функция `useQuery` через props не передаётся.
- В этом примере DataGrid — единственный владелец страницы, размера, сортировки и статуса загрузки; Pagination и Table получают управляемые props. Query-кеш может оставаться внутри сервисной интеграции. Другая схема управления фиксируется как отдельный контракт, а не второй независимый набор запросов.
- Generic-контракт результата может содержать `items` и `total`. Если DTO сервиса имеет другую форму, адаптация выполняется локально в странице/feature, связывающей сервис и DataGrid. Доменное преобразование товаров или пользователей не зашивается в универсальный DataGrid.
- Если сам переиспользуемый бизнес-компонент владеет конкретным DTO-сценарием, его конвертеры остаются внутри этого компонента согласно разделу о DTO.

Если компонент только объединяет Table и Pagination, получает готовые строки и сообщает о событиях, он остаётся UI-organism: композиция организмов сама по себе не создаёт business pattern.

Дополнительный пример: `EditableTable` проверяет изменения по переданной схеме, вызывает `saveChanges`, ожидает результат и отображает ошибки операции. Если он только показывает редактируемые ячейки и сообщает об изменении значений, он также может оставаться UI-organism.

```text
patterns/
  dataGrid/
    index.ts
    DataGrid.tsx
    DataGrid.interface.ts
    DataGrid.hooks.ts
```

#### `features/` - Конкретные бизнес-сценарии

- Реализуют конкретный сценарий приложения, например редактирование товара или ProductsGrid: подключает сервис товаров, задаёт колонки и локально адаптирует контракт для DataGrid.
- Могут импортировать services и store: вызывать операции сервисов, читать состояние и вызывать действия store. Эти импорты допустимы, но не обязательны.
- Могут использовать UI, layouts и patterns.
- Принимают необходимые идентификаторы, данные, callbacks и визуальные настройки; искусственного ограничения только визуальными props нет.
- Каждый бизнес-домен получает подпапку: `product/`, `user/`, `order/`. `cards/` и `table/` — формы отображения, а не бизнес-домены.
- Локальные DTO-преобразования остаются внутри feature.

```text
features/
  product/
    productEditor/
      index.ts
      ProductEditor.tsx
      ProductEditor.interface.ts
      ProductEditor.hooks.ts
      utils/
        productFromDto/
          index.ts
          productFromDto.ts
        productToDto/
          index.ts
          productToDto.ts
    productsGrid/
      index.ts
      ProductsGrid.tsx
```

#### Граница organisms, patterns и features

| Критерий | UI organism | Business pattern | Business feature |
|---|---|---|---|
| Ответственность | Сложное отображение и UI-взаимодействие | Настраиваемый прикладной процесс | Конкретный сценарий приложения |
| Пример | Table и Pagination | DataGrid с загрузкой | ProductsGrid |
| Callbacks | События UI: сортировка, выбор страницы, изменение значения | Операции: загрузить, проверить, сохранить, обработать результат | Конкретные операции домена |
| Управление внешней операцией | Не выполняет; получает её состояние снаружи | Выполняет операцию, переданную через props | Может подключать сервис непосредственно |
| Импорт реализации services/store | Запрещён | Запрещён | Разрешён, не обязателен |
| DTO-преобразования | Не содержит | Локально, если владеет сценарием | Локально |

**Правило выбора:**
1. Компонент отображает данные и сообщает о взаимодействии — UI.
2. Компонент организует прикладной процесс с переданными правилами и операциями — pattern.
3. Компонент задаёт конкретный бизнес-контекст и подключает зависимости приложения — feature.

Наличие callback, схемы проверки, большого количества элементов или прямого store-импорта по отдельности не определяет категорию. Например, проверка диапазона в контроле дат относится к UI, а проверка и отправка формы с обработкой результата — к прикладному сценарию.

Родитель может загрузить данные в ответ на `onSortChange` таблицы или `onPageChange` пагинации. Они остаются UI, пока только сообщают о взаимодействии и не управляют этой загрузкой.

**Сквозной пример:** ProductsGrid подключает сервис товаров и передаёт операцию в DataGrid → DataGrid организует загрузку и её состояния → Table отображает строки, Pagination вычисляет навигацию. События сортировки и перехода возвращаются в DataGrid и запускают следующий запрос.

## `config` - Конфигурация приложения

Находится в корне проекта (рядом с `package.json`), **не** внутри `src/`.

- **Назначение**: типизированный доступ к env-переменным и feature flags. Единственное место, где читаются `process.env` / `import.meta.env` и т.д.
- **Пример структуры**:

  ```
  config/
    ├── env.ts               # Типизированные env-переменные (API_URL, NODE_ENV и т.д.)
    └── features.ts          # Feature flags (включение/выключение фич)
  ```

- **Правила**:
  - `config/env.ts` читает и проверяет значения; потребители импортируют его публичный API через `config/index.ts`, а не внутренний файл и не `process.env`.
  - `env.ts` валидирует обязательные переменные при инициализации в подходящей среде; отсутствующие обязательные значения — ошибка. Клиентская конфигурация содержит только публичные значения; секреты не экспортируются в браузерный bundle. `.env` находится там, где его ожидает выбранный инструмент.
  - Feature flags — булевы флаги, типизированы, с дефолтами

## `constants` - Глобальные константы приложения

- **Содержит**: только константы-примитивы и конфигурационные объекты без side-effects.
- **Не содержит**: транспортные константы конкретного сервиса — они принадлежат services. Пользовательские сообщения определяет владелец UI/сценария, не HTTP-слой.
- **Примеры файлов**:
  ```
  constants/
    ├── regex.constants.ts
    └── routes.constants.ts
  ```

## `lib` - Утилиты и вспомогательные функции

- **Структура**:
  - `hooks/` - переиспользуемые хуки проекта (используются в нескольких местах)
  - `ts/` - утилиты-дженерики для TypeScript
  - `business/` - утилиты, зависящие от бизнес-логики
  - `utils/` - чистые утилиты без контекста проекта

- **Разделение хуков**:
  - Хук UI/сценария, принадлежащий одному компоненту, находится рядом с ним (`ProductCard.hooks.ts`). Сначала учитывается ответственность: инфраструктурный хук внешних данных остаётся в services даже при одном потребителе.
  - Общий хук без зависимости от services/store/бизнес-компонентов → `lib/hooks/`.
  - Хук интеграции внешних данных, возвращающий DTO, может находиться в services. Хук конкретного сценария остаётся у страницы или бизнес-компонента.
  - Локальные DTO-конвертеры не выносятся в lib даже при совпадении кода: см. «DTO vs внутренние модели».

- **Пример структуры `business/`**:

  ```
  business/
    └── formatters/
        ├── phoneMask/
        │   ├── index.ts
        │   └── phoneMask.ts       # Маска поля
        ├── futureDate/
        │   ├── index.ts
        │   └── futureDate.ts      # Общая проверка даты
        ├── moneyAmount/
        │   ├── index.ts
        │   └── moneyAmount.ts     # Общая проверка суммы
        └── numberFormat/
            ├── index.ts
            └── numberFormat.ts   # Общая проверка числа
  ```

  - Примечание: обобщённые утилиты и Zod-схемы для валидации полей форм. Схемы валидации **ответов API** живут рядом с endpoint-функциями (см. «Валидация данных»).

- **Пример структуры `utils/`**:

  ```
  utils/
    ├── string/
    │   └── declOfNum/
    │       ├── index.ts
    │       └── declOfNum.ts
    └── number/
        └── formatPrice/
            ├── index.ts
            ├── formatPrice.ts
            └── formatPrice.interface.ts # если есть собственные интерфейсы
  ```

- Чистые адаптеры библиотек и общие вычисления могут находиться в lib. Отправка аналитики, внешние запросы и подписки относятся к services; отображение карты и UI-взаимодействие — к компоненту.

## `mocks` - Моковые данные для тестов и разработки

- **Структура**: моки организованы по доменам (как `services/api/`):
  - `service/` - моки API-сервисов, **каждый домен в отдельной папке**
  - `components/` - моки для пропсов компонентов
- **Пример структуры**:

  ```
  mocks/
    ├── service/
    │   ├── auth/
    │   │   └── login.mock.ts
    │   └── user/
    │       └── getUser.mock.ts
    └── components/
        └── cardProfile.mock.ts
  ```

- **Правила**:
  - Моки импортируются из тестов, stories, отдельной точки входа демо и их изолированной инфраструктуры (setup/decorators). Демо-entry и mock worker не включаются в production-сборку. В production-модули они не импортируются.
  - Допустимы небольшие инлайн-данные и общие fixtures из `mocks/`. Fixtures детерминированы и не выполняют реальные внешние запросы при импорте.
  - Если тест или story меняет данные, создавай отдельный экземпляр через фабрику, чтобы состояние не переходило между сценариями.
  - Моки могут импортировать типы контрактов через `import type`; для получения тестовых данных не вызываются production-сервисы.
  - **Каждый домен = отдельная папка** (не класть все моки в одну папку)

## `services` - Работа с side-эффектами

- **Назначение**: слой внешних взаимодействий: HTTP, localStorage, sessionStorage, cookies, обмен между вкладками. Предоставляет операции чтения, записи и подписки с освобождением ресурсов.
- **Контракт**: принимает и возвращает DTO, при необходимости проверяет схему DTO. Не преобразует данные под формы, страницы или внутренние модели store.
- **Правило**: services не импортируют app, компоненты или store. Кто вызывает сервис, тот решает, как использовать результат.
- **Реализация**: обычные методы (например, fetch) либо React Query/SWR hooks и query-конфигурации внутри сервиса. Они сохраняют внешний контракт; преобразования под сценарий остаются у потребителя.
- **Граница эффектов**: здесь находится реализация внешнего взаимодействия. Страница/feature вызывает её напрямую; pattern может вызвать переданную операцию. Локальные UI-эффекты не обязаны находиться в services.
- **Важно**: **каждый домен = отдельная папка** в `api/`. Не класть все endpoint-функции в одну папку.

### Варианты API-слоя

На старте проекта выбрать **один** вариант и зафиксировать в документации. Инструменты выбираются по [React-профилю](ReactPreferences.md).

Общая транспортная механика (создание HTTP-клиента, timeout, классификация ошибок) не привязана к бизнес-сущности. Конкретная интеграция настраивает baseURL и свои протокольные особенности; её доменные методы описывают endpoint и DTO. Не называем общий транспорт именем одной сущности и не переносим специфичную авторизацию поставщика в универсальный клиент.

По умолчанию у приложения один HttpClient с общей конфигурацией. Дополнительные инстансы нужны только независимым внешним интеграциям с различающимися настройками; не создаём клиент на каждую сущность или endpoint. В [исполняемом примере](../examples/react-reference/README.md): services/api/httpClient содержит единственный инстанс и обработку ошибок; services/api/connection — DTO и mutation с непосредственным вызовом клиента.

Если endpoint нужен только одному query/mutation-хуку, запрос выполняется прямо в его queryFn/mutationFn. Отдельный метод выделяется при самостоятельных потребителях или отдельной ответственности, а не ради одноразовой обёртки. Оба варианта остаются внутри services и возвращают DTO.

### API-клиент — контракт реализации

`client.ts` создаёт настроенный HTTP-клиент. Библиотека выбирается проектом; клиент предоставляет типизированный результат и параметры отдельного запроса. Ниже минимальный пример для JSON API, а не обязательная обёртка над библиотекой с равнозначным контрактом.

```ts
// services/types/requestOptions.interface.ts
export interface RequestOptions {
  params?: Readonly<Record<string, string | number | boolean | undefined>>;
  headers?: Readonly<Record<string, string>>;
  signal?: AbortSignal;
  timeoutMs?: number;
}
```

```ts
// services/api/client.interface.ts
import type { RequestOptions } from "../types";

export interface ApiClient {
  get<T>(url: string, options?: RequestOptions): Promise<T>;
  post<T>(url: string, body?: unknown, options?: RequestOptions): Promise<T>;
  put<T>(url: string, body?: unknown, options?: RequestOptions): Promise<T>;
  patch<T>(url: string, body?: unknown, options?: RequestOptions): Promise<T>;
  delete<T>(url: string, options?: RequestOptions): Promise<T>;
}
```

`services/types/index.ts` экспортирует `RequestOptions`. Endpoint передаёт параметры запроса клиенту: отмена доходит до транспорта и ожидания retry; timeout можно задать на запрос. Тип результата `T` не является runtime-валидацией: схема проверяется отдельно, если это требуется контрактом сервиса.

```ts
// Фрагмент services/api/user/getUser.ts.
// client — настроенный экземпляр; DTO принадлежит домену user.
// RequestOptions импортируется через публичный индекс services/types.
export const getUser = (
  id: string,
  options?: RequestOptions,
): Promise<UserResponseDto> =>
  client.get<UserResponseDto>(`/users/${encodeURIComponent(id)}`, options);
```

Сервис сохраняет response DTO без преобразования под UI. Для успешного ответа без тела endpoint возвращает `Promise<void>`, а клиент не пытается разбирать пустое тело как JSON. Поддержка загрузки файлов и других форматов определяется отдельно по API приложения; при передаче FormData браузер формирует Content-Type с boundary.

### Конфигурация клиента

| Параметр               | Откуда берётся                                | Описание                                                     |
| ---------------------- | --------------------------------------------- | ------------------------------------------------------------ |
| Base URL               | env-переменная (`API_URL` и т.д.)             | Не захардкожен в коде, читается из конфигурации окружения    |
| Timeout                | константа в `client.ts` (по умолчанию 30 сек) | Меняется per-request при необходимости                       |
| Заголовки по умолчанию | `client.ts`                                   | `Accept: application/json`; `Content-Type: application/json` только для JSON-тела |

### Interceptors — жизненный цикл запроса

```
Request pipeline:
  [1] auth.ts        → подставить токен в заголовки
  [2] (запрос уходит)
  [3] errorHandler.ts → классифицировать ошибку без пользовательских уведомлений
  [4] retry.ts        → проверить временный характер ошибки, политику операции и лимит
      разрешён повтор → дождаться задержки и повторить запрос
  [5] результат или окончательная ошибка → вызывающий код
```

**auth.ts** — контракт:

- Читает токен через выбранный сервис хранения (например, `services/localStorage/` или `services/cookies/`).
- Подставляет в `Authorization: Bearer {token}`
- При 401 → выполняет предусмотренный контрактом refresh либо возвращает ошибку авторизации. Решение о переходе на логин принимает app/feature.
- Не содержит бизнес-логику, только механику токена

**errorHandler.ts** — контракт:

- Маппит HTTP-статус-коды в типизированные ошибки приложения
- 400 → ошибка некорректного запроса; `ValidationError` только если тело ответа соответствует контракту ошибок полей. Конкретные API могут использовать для них 422.
- 401 → `UnauthorizedError`; сброс состояния и переход организует app/feature
- 403 → `ForbiddenError`
- 404 → `NotFoundError`
- 429 → ошибка ограничения частоты запросов, 500+ → `ServerError`
- Network error → `NetworkError`; timeout и явная отмена различаются отдельными кодами
- Все ошибки реализуют общий интерфейс `AppError`

**retry.ts** — контракт:

- Network error, timeout, 429 и 503 — кандидаты на повтор, а не безусловное разрешение.
- Повтор допустим только для операции, безопасной для повторного выполнения по серверному контракту. Потерянный ответ не означает, что сервер не выполнил запрос.
- В принятой политике по умолчанию повторяем только идемпотентное чтение GET/HEAD. Для PUT/DELETE и других операций повтор включается явно с учётом контракта endpoint.
- POST/PATCH автоматически не повторяем без гарантии идемпотентности конкретной операции. Например, сервер может поддерживать ключ идемпотентности: при повторах одной операции используются тот же ключ и те же данные. Одного добавления заголовка без поддержки сервером недостаточно.
- Не повторяем отменённые запросы, ошибки проверки DTO и 400/401/403/404. Refresh после 401 — отдельный ограниченный механизм, а не общий retry.
- Максимум **3 попытки всего**: первоначальный запрос и до двух повторов. Базовые задержки перед повторами — 1 и 2 секунды; можно добавить jitter. Отмена прерывает ожидание.
- Для 429/503 валидный `Retry-After` (число секунд либо HTTP-дата) задаёт минимальное ожидание. Если оно выходит за общий временной бюджет операции, возвращаем ошибку вместо более раннего повтора; при отсутствии/некорректном заголовке применяется backoff.
- Retry контролируется в одном месте: HTTP-клиентом либо React Query/SWR-интеграцией. Не включаем независимые повторения на обоих уровнях.
- Пользовательское уведомление об ошибке формируется после окончательного отказа, а не на каждой попытке.

Ограничения повторного выполнения: [HTTP Semantics, идемпотентные методы](https://www.rfc-editor.org/rfc/rfc9110.html#section-9.2.2). Лимит попыток и задержки выше — соглашение проекта.

### Обработка ошибок — типизация

```ts
// services/types/error.interface.ts — пример

interface AppError {
  code: ErrorCode;
  message: string;
  status?: number;        // HTTP-статус (если HTTP-ошибка)
  details?: unknown;      // Тело ошибки от сервера (validation errors и т.д.)
  isRetryable: boolean;   // Ошибка допускает рассмотрение retry; дополнительно проверяется политика операции
}

type ErrorCode =
  | 'NETWORK_ERROR'       // Нет соединения
  | 'TIMEOUT'             // Таймаут запроса
  | 'UNAUTHORIZED'        // 401
  | 'FORBIDDEN'           // 403
  | 'NOT_FOUND'           // 404
  | 'VALIDATION'          // Ошибки полей по контракту API (например, 400/422)
  | 'BAD_REQUEST'         // 400 без распознанного контракта ошибок полей
  | 'RATE_LIMIT'          // 429
  | 'ABORTED'             // Явная отмена, не повод для retry
  | 'SERVER'              // 500+
  | 'UNKNOWN';            // Всё остальное
```

### DTO vs внутренние модели

Это основной раздел о владении преобразованиями. DTO описывает внешний контракт, внутренняя модель — потребности конкретного сценария или store.

| Представление | Владелец |
|---|---|
| DTO запроса/ответа | Контракт сервиса |
| Значения формы, view model | Страница или бизнес-компонент, которому они нужны |
| Модель состояния приложения | Store-модуль; не зависит от DTO |
| Преобразование DTO ↔ локальная модель | Страница или бизнес-компонент-потребитель |

**Правила:**
- Страница или feature получает сырой DTO из сервиса; pattern может получать DTO и операции через props.
- Преобразование выполняется локально под требования потребителя. Файлы и функции называются `{entity}FromDto` и `{entity}ToDto`: например, `utils/cardFromDto/cardFromDto.ts` и `utils/cardToDto/cardToDto.ts`, каждый со своим `index.ts`.
- Конвертеры не размещаются в `lib/`, `services/` или `store/` и не импортируются одной страницей из другой.
- Совпадение DTO и реализации на двух страницах не является основанием для объединения: сценарии могут развиваться независимо. Одинаковые имена локальных конвертеров допустимы.
- Если переиспользуется целый сценарий, его UI, поведение и преобразования переносятся вместе в business pattern или feature.
- Низкоуровневые общие функции можно использовать из lib, если они не знают о DTO endpoint и форме конкретной страницы.
- Если представление не меняется, не нужен пустой identity-конвертер. Передача в store всё равно должна соответствовать его собственному контракту и не связывать store с DTO.
- Проверка схемы DTO в services и преобразование модели — разные операции.

```text
pages/
  cardEditPage/
    index.ts
    CardEditPage.tsx
    CardEditPage.interface.ts
    utils/
      index.ts                  # Доступ внутри страницы, не общий API приложения
      cardFromDto/
        index.ts
        cardFromDto.ts
      cardToDto/
        index.ts
        cardToDto.ts
    _components/
      cardEditForm/
        index.ts
        CardEditForm.tsx
        CardEditForm.interface.ts
```

**Поток редактирования:**

```text
service → response DTO
        → cardFromDto → значения формы
        → редактирование → проверка формы, если предусмотрена
        → cardToDto → request DTO → service
```

**Пример входящего преобразования** — фрагмент модуля страницы; DTO экспортируются доменным индексом `services/api/user`, локальные типы — `profilePage/ProfilePage.interface.ts`. Примеры предполагают настроенный алиас `@/` для `src/`.

```ts
// pages/profilePage/utils/userFromDto/userFromDto.ts
import type { UserResponseDto } from "@/services/api/user";
import type { UserFormValues } from "../../ProfilePage.interface";

export const userFromDto = (dto: UserResponseDto): UserFormValues => {
  return {
    firstName: dto.first_name,
    email: dto.email,
  };
};
```

**Пример исходящего преобразования:**

```ts
// pages/profilePage/utils/userToDto/userToDto.ts
import type { UserRequestDto } from "@/services/api/user";
import type { UserFormValues } from "../../ProfilePage.interface";

export const userToDto = (form: UserFormValues): UserRequestDto => {
  return {
    first_name: form.firstName,
    email: form.email,
  };
};
```

Страница также может получить DTO из API и storage, собрать из них внутреннюю модель текущего клиента и передать её действию store. Store не выполняет получение или преобразование.

### Endpoint-функции — контракт

Endpoint возвращает `Promise<T>` и передаёт параметры запроса клиенту. Пример `getUser` находится в [контракте API-клиента](#api-клиент--контракт-реализации).

**Правила**:

- Endpoint возвращает **DTO**, не бизнес-модель
- Конвертацию делает страница или бизнес-компонент-потребитель; конвертер лежит внутри его модуля. Store не вызывает endpoint и не преобразует DTO.
- Каждый endpoint — одна функция, один файл (или несколько мелких в одном файле, если они связаны)
- Никакой бизнес-логики в endpoint-функциях — только вызов клиента с параметрами
- **Каждый домен = отдельная папка**: `services/api/auth/`, `services/api/user/`, `services/api/product/`

### Правила слоя services

- `services/` не импортирует из `components/`, `store/`, `app/`, `pages/`, `routes/`
- `services/` может импортировать из `lib/` (утилиты, типы)
- Endpoint-функции возвращают DTO, не бизнес-модели
- Механика внешнего токена живёт в services. Внутренняя модель сессии может жить в store; связывает их app/feature.
- Все env-переменные типизированы: `config/env.ts` владеет чтением, потребители используют публичный индекс `config/`.

### Валидация данных

- **Принцип**: по умолчанию доверяем контрактам с бэкендом. API отдаёт валидированные данные, клиент не дублирует валидацию.
- **Валидация ответов API**: только при явном требовании (нестабильный API, миграция, отсутствие контрактов). Схемы живут **рядом с endpoint-функцией**:
  ```
  services/
    └── api/
        └── auth/
            ├── login.ts
            └── login.schema.ts    # Zod-схема для валидации ответа login
  ```
- **Валидация форм**: сервер проверяет свои ограничения. Клиентская проверка применяется для UX по требованиям сценария. Схема всей формы остаётся рядом со страницей/бизнес-компонентом; общие проверки отдельных полей могут находиться в `lib/business/formatters/` по правилам lib.
- **При отсутствии требования к клиентской валидации**: отдельная проверка формы не обязательна. Перед отправкой локальный `toDto` формирует request DTO, если представления различаются. Endpoint получает DTO, а не произвольное UI-состояние.

## `store` - Клиентское состояние

Store владеет внутренним состоянием приложения и операциями над ним. Он не знает о способе получения данных, не импортирует services, не принимает DTO как свой контракт и не выполняет внешние запросы.

**Данные, полученные на основе внешних источников, хранить разрешено.** Страница или feature преобразует их во внутреннюю модель и передаёт действию store. Происхождение данных не определяет допустимость хранения; её определяет ответственность store.

- Примеры: UI state, текущий клиент, состояние сессии, preferences, черновики форм, локальная корзина.
- Типы состояния принадлежат store-модулю и не импортируют типы DTO из services.
- Store не содержит DTO-конвертеров, endpoint-функций или query hooks.
- Доступ к API, localStorage, sessionStorage, cookies и обмену между вкладками остаётся в services. Страница/feature организует чтение, преобразование и запись; store не подключает storage самостоятельно.
- Имена файлов зависят от выбранного state-менеджера.
- Каждый домен получает отдельную папку.

```text
store/
  store.ts
  auth/
    authStore.ts
    authSelectors.ts
    types/
      currentClient.interface.ts
  ui/
    uiStore.ts
    uiSelectors.ts
  cart/
    cartStore.ts
    cartSelectors.ts
```

### Server state и внутреннее состояние

Service может предоставлять обычные методы или React Query/SWR-интеграцию. Его данные сохраняют внешний DTO-контракт; query-кеш и статусы получения относятся к механизму внешних данных. Преобразование под страницу или бизнес-компонент остаётся у потребителя.

```text
API DTO + storage DTO
        ↓
страница / feature: локальное преобразование и объединение
        ↓
внутренняя модель текущего клиента
        ↓
действие store
```

Стрелки показывают передачу данных, не направление импортов. Services и store не импортируют друг друга.

| Критерий | Services / query-кеш | Store |
|---|---|---|
| Ответственность | Получение, запись, подписки, внешний контракт | Внутреннее состояние приложения |
| Представление | DTO | Внутренняя модель |
| Зависимость от другого слоя | Не импортирует store | Не импортирует services |
| Преобразование под сценарий | Не выполняет | Не выполняет |
| Кто связывает слои | Страница или feature; pattern через переданные операции | Тот же владелец сценария |

Сохранение внутренней модели в store не означает автоматическое копирование всех query-данных. Для сохраняемой модели владелец сценария определяет момент обновления и сброса, например загрузку текущего клиента после входа и очистку при выходе. Конкретную политику фиксируют в проекте.

## Storybook

- **Назначение**: Storybook — обязательная визуальная документация UI в React-профиле. Настраивается вместе с первыми UI-примитивами и показывает их состояния и взаимодействия. См. [предпочтения UI](ReactPreferences.md#ui-и-storybook).
- **Расположение**: stories живут **рядом с компонентом** (не в отдельной папке):
  ```
  button/
    ├── button.css
    └── Button.stories.tsx     # ← здесь
  ```

### Какие компоненты **обязаны** иметь story

| Слой                 | Story обязателен | Причина                                                               |
| -------------------- | ---------------- | --------------------------------------------------------------------- |
| `ui/atoms/`          | Да               | Базовые строительные блоки, должны быть задокументированы             |
| `ui/molecules/`      | Да               | Переиспользуемые композиции, разработчики должны видеть все состояния |
| `ui/organisms/`      | Да               | Сложные блоки, требуют интерактивной демонстрации                     |
| `business/layouts/`  | Опционально      | Макеты без логики, story полезна для визуальной проверки              |
| `business/patterns/` | Опционально      | Шаблонные компоненты с большим количеством конфигураций               |
| `business/features/` | Опционально      | Для изоляции используются тестовые зависимости; store не обязателен |

Требование stories действует по умолчанию. Отсутствие настроенного инструмента — незавершённый этап внедрения, а не автоматическое исключение. Отказ от Storybook или его замена требуют явного решения владельца проекта; после согласования в паспорте фиксируются причина и альтернативный способ проверки UI. Маленький размер проекта и CSS-реализация атомов не дают автоматического исключения. Установку инструмента выполняют в рамках задачи на настройку, а недоступные проверки отражают в отчёте.

### Структура story-файла

Story-файл описывает компонент или CSS-примитив и его состояния. Ниже используются термины Storybook; при другом инструменте соответствующие API фиксируются в паспорте проекта.

**Каждый story-файл содержит:**

1. **Мета-описание** — название в sidebar, привязка к компоненту, если он существует, и настройка документации. Для CSS-атомов используется демонстрационная HTML-разметка, production-компонент не требуется.
2. **Описание controls** — маппинг пропсов на типы контролов (select, boolean, radio и т.д.)
3. **Набор stories** — каждый экспорт story описывает состояние; метаданные и технические экспорты следуют контракту инструмента.

**Обязательные stories:**

| Story                     | Назначение                                                    |
| ------------------------- | ------------------------------------------------------------- |
| `Default`                 | Базовое состояние по соглашению проекта; имя не задаёт порядок открытия |
| Все значения enum-пропсов | Визуальное покрытие всех вариантов (`variant`, `size` и т.д.) |

**Желательные stories:**

| Story              | Назначение                                           |
| ------------------ | ---------------------------------------------------- |
| Loading / Disabled | Состояния взаимодействия                             |
| Edge cases         | Длинный текст, пустое содержимое, граничные значения |
| Адаптив            | Проверка через viewport toolbar                      |

### Правила

- **Один story-файл на компонент**: `Button.stories.tsx` — не `Button.variants.stories.tsx` + `Button.states.stories.tsx`
- **Автодокументация**: для компонентов включать механизм, поддерживаемый выбранной версией инструмента. Для CSS-атомов документировать классы и состояния вручную: props production-компонента у них нет.
- **Controls**: описывать для props с ограниченным набором значений; у CSS-атомов controls управляют демонстрационной разметкой.
- **Naming экспорта**: английский `PascalCase`. Отображаемое название может быть русским. `Default` — обязательное имя базовой story по соглашению проекта, а порядок задаётся настройками и порядком stories выбранного инструмента.
- **Изоляция**: story не обращается к реальным внешним сервисам. Patterns получают тестовые callbacks с управляемым результатом; для features при необходимости используются изолированные провайдеры и тестовое состояние.
- **Mock-данные**: допустимы инлайн-данные и общие fixtures из `mocks/` согласно [правилам моков](#mocks---моковые-данные-для-тестов-и-разработки). Story должна воспроизводиться изолированно, без реального backend и зависимости от запуска других stories.

## Сквозной пример: редактирование карточки

Это пример распределения ответственности, а не готовое приложение или дополнительный слой архитектуры. Конкретные типы, UI и команды определяются проектом. Сервис предоставляет операции получения и обновления карточки; страница владеет сценарием редактирования.

### Владельцы кода

| Модуль | Ответственность |
|---|---|
| services/api/card | Получить response DTO, принять request DTO для обновления; при необходимости проверить внешний контракт |
| pages/cardEditPage | Загрузить карточку, организовать состояния экрана, редактирование и сохранение |
| Локальные cardFromDto/cardToDto | Преобразовать данные именно для этой формы |
| Локальная CardEditForm | Показать поля, изменения и ошибки; сообщить о submit |
| UI | Отобразить поля, подписи, индикаторы и сообщения без подключения сервиса |
| Store | В этом сценарии не нужен, пока нет самостоятельной потребности в общем внутреннем состоянии |

Структура с локальной формой и преобразованиями приведена в [контракте DTO](#dto-vs-внутренние-модели). Каждый модуль публикует выбранные сущности через индекс по [правилам API](ProjectStructure.md#дерево-публичных-экспортов); внутренние конвертеры экспортируются из собственных папок для кода страницы, но не включаются в публичный API самой страницы.

### 1. Загрузка

Страница получает id из маршрута и вызывает сервис напрямую либо через предусмотренную сервисом query-интеграцию. Пока запрос выполняется, показывает loading. Отсутствующая карточка имеет отдельное состояние «не найдена»; сетевой отказ — ошибку с возможностью повторить разрешённую операцию.

Если пользователь перешёл к другой карточке, устаревший ответ не должен заменить актуальный. Владелец загрузки отменяет предыдущий запрос либо игнорирует его результат. Получение данных не выполняется UI-полями.

### 2. Локальное представление и редактирование

Например, response DTO содержит price_cents: 1250, а форма показывает редактируемое строковое поле price: "12.50". Локальный cardFromDto создаёт представление этой страницы. Идентификаторы, необязательные поля и формат денежных значений определяются контрактом, а не универсальным преобразователем.

Форма хранит редактируемый черновик локально. Фоновое обновление запроса не должно молча уничтожать несохранённый ввод: проект выбирает явное поведение, например уведомление о новой версии. Состояние dirty относится к форме, не к transport DTO.

Схема всей формы находится рядом со сценарием. Общие проверки полей могут использоваться из lib по существующим правилам. Вторая страница с похожей формой сохраняет собственные преобразования, пока не выделен целый общий бизнес-сценарий.

### 3. Проверка и отправка

При submit выполняется предусмотренная проверка формы. Для денежного поля она различает пустую строку, неверный формат, недопустимую точность и диапазон. Правила округления и перевод в минимальные единицы согласуются с API; простое умножение произвольного Number на 100 не считается универсальным решением.

После успешной проверки cardToDto формирует request DTO, например price_cents: 1250. В запрос попадают поля контракта, а не весь UI-объект формы со служебными состояниями.

Владелец сценария вызывает сервис сохранения и отслеживает pending. Повторный submit во время отправки не создаёт параллельную операцию. Автоматические повторы применяются только по [контракту retry](#interceptors--жизненный-цикл-запроса).

### 4. Результат операции

- При ошибке проверки со стороны сервера сохраняется пользовательский ввод, ошибки связываются с полями либо показываются как общая ошибка формы.
- При сетевой ошибке форма остаётся доступной для исправления или разрешённого повторного действия; успех не показывается.
- При успешном сохранении владелец сценария обновляет query-кеш из ответа либо инициирует повторное получение — по одному выбранному подходу; без query-кеша обновляет локально загруженные данные из ответа или повторным запросом. Сервисная query-интеграция может управлять внешним кешем, но не внутренним store.
- Для чистого черновика принятые сервером данные проходят через локальный fromDto. Если ввод изменялся во время запроса, новый ввод не теряется: на время submit редактирование блокируется либо версия черновика учитывается явно.
- Данные не копируются в store только ради доступности. Если сохраняемое изменение затрагивает самостоятельную внутреннюю модель приложения, страница/feature передаёт её действию store и определяет момент обновления.

### Когда сценарий становится общим

Если нужен тот же сценарий целиком на нескольких страницах, он переносится в business feature с подключением конкретного сервиса или в pattern с переданными операциями. Вместе с ним переезжают его форма, поведение и локальные преобразования. Одно лишь совпадение DTO не является причиной переноса.

### Что проверить в примере

| Ситуация | Ожидаемый результат |
|---|---|
| Успешная загрузка | Поля заполнены локальным представлением DTO |
| Смена id во время загрузки | Поздний старый ответ не меняет новую карточку |
| Карточка отсутствует / запрос отклонён | Правильное отдельное состояние, без ложного успеха |
| Неверное значение формы | Отображена ошибка; при клиентской проверке запрос не отправлен |
| Корректный submit | Сервис получил request DTO, а не UI-состояние |
| Повторный submit во время pending | Параллельная операция не создана |
| Ошибка сохранения | Ввод сохранён, ошибка видима |
| Успех | Отображаются принятые данные, кеш обновлён выбранным способом |
| Фоновое обновление при dirty-форме | Нет незаметной потери ввода |

## Готовность изменения и проверки

Этот раздел задаёт общий минимум. Конкретные команды и инструменты находятся в [паспорте проекта](../README.md#паспорт-проекта). В корне toolbox нет команд приложения; рабочие команды учебного примера перечислены в [его README](../examples/react-reference/README.md). Таблица ниже не является отчётом об уже выполненных тестах.

### Критерии готовности

- Выполнен запрошенный пользовательский сценарий и рассмотрены существенные для него ошибки и граничные состояния.
- Расположение, импорты и публичный API соответствуют основным контрактам; чужие изменения сохранены.
- При изменении поведения проверены затронутые потребители; не требуется перепроверять несвязанные части без причины.
- Выполнены проверки существенного поведения. Постоянные тесты добавляются по требованиям задания и согласованному объёму; первая итерация не подразумевает автоматическую установку test-framework. Порядок определён в [React-профиле](ReactPreferences.md#первая-итерация). Не нужны тесты ради каждого файла или копирования реализации.
- Запущены применимые доступные проверки. Неудачные или недоступные проверки перечислены с причиной, а не скрыты.
- Изменённый контракт отражён в документации и примерах. Для одной правки текста не требуется запуск приложения.

### Выбор проверок

| Изменение | Проверка по применимости |
|---|---|
| Конвертер/вычисление | Вход/выход, значимые границы, отсутствие случайной мутации |
| Сервис | DTO-контракт, ошибки, отмена, допустимость retry; интеграционные проверки с изолированными ответами |
| Компонент/форма | Пользовательское взаимодействие и видимые состояния |
| Критический сценарий | Сквозная проверка в настроенном приложении |
| Публичный API/перенос | Импорты потребителей, typecheck и сборка, если настроены |
| UI-кит | Stories для обязательных слоёв, визуальная проверка и доступность |
| Документация | Локальные ссылки, согласованность примеров, diff |

Stories помогают демонстрировать состояния, но само наличие story не подтверждает прохождение проверок поведения. Моки должны воспроизводиться изолированно по [контракту mocks](#mocks---моковые-данные-для-тестов-и-разработки).

### Минимум доступности UI

Для изменённых интерактивных элементов проверяются подходящий HTML-элемент, доступное имя, работа клавиатурой и видимый focus. Поля связаны с подписями и сообщениями об ошибках; состояние загрузки/ошибки не передаётся только цветом.

Применение button-стиля к ссылке не меняет её назначение: навигация остаётся ссылкой, действие — кнопкой. В Pagination обозначается текущая страница и корректно обрабатываются недоступные переходы; конкретная реализация определяется UI-контрактом.

### Отчёт об изменении

Результат работы содержит: выполненное изменение, проведённые проверки и их исход, а также оставшиеся ограничения. Коммит, push и успешные тесты указываются только если действительно выполнены.
