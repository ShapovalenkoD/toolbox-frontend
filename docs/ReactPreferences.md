# React: предпочтения и старт проекта

Основной профиль этих соглашений — React и TypeScript. При адаптации к другому framework создаётся отдельный согласованный профиль. Архитектура, публичный API и стиль остаются в своих [основных документах](../README.md#документация).

Основной ориентир по личным предпочтениям — cs2_frontend. Его Next.js-специфика не является требованием использовать Next.js в любом приложении. Старые ошибки, отключённые проверки и зависимости на конкретный backend не копируются автоматически.

## Предпочтительные решения

| Область | Предпочтение | Когда подключать |
|---|---|---|
| Основа | React + TypeScript | Базовый профиль |
| Клиентское приложение | Vite | Когда не нужны возможности meta-framework |
| Next.js | Допустим и знаком | При потребности в его routing, server rendering и других возможностях |
| Форматирование, lint и сортировки | Только Biome, ориентир — cs2_frontend | С начала проекта; ESLint, Prettier и их плагины не добавляем |
| UI | Собственные стили и компоненты | Готовый оформленный UI-кит по умолчанию не устанавливается |
| Позиционирование и взаимодействия | Floating UI для React | Tooltip, popover, dropdown и похожие задачи; поведение и доступность реализуются явно |
| Таблицы | TanStack Table | Когда требуется табличная модель: сортировка, столбцы, фильтрация и т.п. |
| Виртуализация | TanStack Virtual | При реальной потребности в больших списках/таблицах |
| Карусель/слайдер | embla-carousel-react | Малый вес и мало зависимостей; вместо самописной логики свайпов/автопрокрутки. UI-organism (см. [organisms](ProjectStructure.full.md#organisms---сложные-блоки)) |
| Datepicker/календарь | react-datepicker — знакомый вариант | Вместо самописного календаря с расчётом дат, локалей и диапазонов |
| Работа с датами (вычисления, парсинг, диапазоны) | date-fns | Для арифметики и разбора дат сложнее форматирования. Простое отображение (formatDate/formatTime на Intl, см. [lib/utils](ProjectStructure.full.md#lib---утилиты-и-вспомогательные-функции)) не требует подключения библиотеки |
| Toast-уведомления | sonner | Пользовательские уведомления об успехе/ошибке операции вне формы |
| Навигация SPA | TanStack Router | Если приложению нужны маршруты; не добавлять второй router поверх Next.js |
| Серверные данные | TanStack Query | Для согласованного управления запросами, mutation, кешем и их состояниями |
| HTTP | Axios — знакомый вариант | Выбор транспорта фиксируется в проекте; небольшой fetch-сервис допустим по решению задачи |
| Формы | React Hook Form + Zod | Для форм со значимыми состояниями/валидацией; учитываем выбранный framework |
| Стили | Tailwind предпочтителен, необязателен | CSS/CSS Modules тоже допустимы |
| Объединение CSS-классов | clsx | Только без Tailwind; без самописного filter(Boolean).join |
| Объединение Tailwind-классов | tailwind-merge | Обязателен, если выбран Tailwind; clsx при этом не используем |
| Визуальная документация | Storybook | Обязательная часть разработки UI в React-профиле |
| Генерация моковых данных | @faker-js/faker | Когда нужны разнообразные наборы fixtures; простые фиксированные примеры допустимы |
| Подмена HTTP для демо/stories | MSW — подходящий вариант | При необходимости изолировать внешние запросы; обязателен для stories business/features, которые сами вызывают services напрямую — см. [Storybook](ProjectStructure.full.md#storybook) |
| Внутренний store | Zustand + immer — знакомый вариант, слайсы по [примеру store](ProjectStructure.full.md#store---клиентское-состояние) | Только при самостоятельной потребности в общем внутреннем состоянии |
| Codegen | Orval — знакомый вариант | При наличии подходящей схемы API и принятом решении о генерации |

Это каталог предпочтений, а не список обязательной установки целиком. Выбор библиотеки должен уменьшать объём поддерживаемой вручную инфраструктуры и соответствовать задаче. Не заменяем подходящее готовое решение собственным мини-framework только ради меньшего числа пакетов.

Headless-подход, небольшой размер и количество транзитивных зависимостей — отдельные характеристики. Не называем весь каталог «zero dependency» и не предполагаем, что любая библиотека в нём не имеет зависимостей.

Случайные транзитивные/точечные зависимости отдельного старого проекта (например, `lodash.merge`/`lodash.mergewith` в altera_crm_front) в этот каталог сознательно не включены — их наличие в старом проекте не делает их предпочтением по умолчанию для новых задач.

## Библиотека вместо самописного решения для тяжёлых задач

Для функциональности с большим объёмом состояния, edge-кейсов и требований к доступности — таблицы с сортировкой/фильтрацией, датапикеры и календари, карусели, комбобоксы и автокомплиты, drag-and-drop, генерация API-клиента по схеме — предпочитаем готовую библиотеку из каталога выше (или подходящую по тем же критериям, если сценарий не покрыт каталогом), а не собственную реализацию с нуля. Самописный код для таких сценариев обычно означает необходимость самим закрывать то, что уже решено в библиотеке: клавиатурную навигацию, локализацию, edge-кейсы дат/таймзон, производительность на больших данных. Небольшая точечная задача (простая маска поля, форматирование одного значения) не требует подключения библиотеки ради одной функции — см. [lib/business/formatters](ProjectStructure.full.md#lib---утилиты-и-вспомогательные-функции).

Если для конкретной задачи нет готового предпочтения в каталоге выше, оценивай кандидата по трём критериям, проверяя актуальные данные (npm/GitHub), а не по памяти:

- **Зависимости**: чем меньше собственных runtime-зависимостей у библиотеки, тем меньше транзитивный риск — ориентир: пакеты уровня TanStack, где ядро почти не тянет чужой код.
- **Соотношение открытых issues к звёздам**: чем меньше открытых issues относительно популярности (звёзд) — тем здоровее сопровождение. Большое абсолютное число issues при ещё большей популярности не тревожный признак само по себе; тревожный признак — когда issues растут быстрее, чем они закрываются.
- **Активность поддержки**: коммиты и релизы за последние месяцы, а не заброшенный год назад репозиторий; живое сообщество (обсуждения, реакция мейнтейнеров на issues/PR).

Выбор фиксируется в паспорте проекта вместе с обоснованием, если он не следует напрямую из каталога выше.

## UI и Storybook

Сохраняем собственный внешний вид и разделение foundation → atoms → molecules → organisms. Низкоуровневая библиотека отвечает за свою механику, но не отменяет архитектурную ответственность компонента.

Storybook настраивается вместе с первыми UI-примитивами. Обязательность stories и их состояния описаны в [полной структуре](ProjectStructure.full.md#storybook). Маленький проект и отсутствие production React-компонента у CSS-атома не являются причинами пропустить story.

Foundation разделяется по назначению файлов; atoms предоставляют базовый CSS-класс. Модификаторы размеров и вариантов добавляем только при реальной потребности, по правилам полной структуры. Production Button/Input-обёртки ради variant не создаются. Story атома использует его классы на HTML-элементе. TextField и LoadingButton показывают композицию и состояния.

Готовый оформленный UI-кит или отказ от Storybook требуют отдельного явного решения владельца проекта. Нельзя самостоятельно объявить исключение в README и считать его согласованным.

## Tailwind

При выборе Tailwind:

- Устанавливаем совместимую с его версией tailwind-merge. Это единственный инструмент объединения классов; clsx и обёртки twMerge(clsx(...)) не используем.
- Используем twMerge при объединении потенциально конфликтующих utility-классов, например базовых классов и className потребителя. Простое соединение строк не разрешает такие конфликты.
- Настраиваем порядок классов в className и используемых функциях, включая twMerge/twJoin.
- В Biome используем подходящую текущей версии настройку useSortedClasses.
- Проверяем работу правила на конфигурации проекта, включая собственные utilities. Не включаем второй конкурирующий форматтер для тех же файлов.
- Длинный набор классов в twMerge/twJoin разбиваем на несколько аргументов по смыслу (раскладка, отступы, рамка, фон, адаптивность), а не пишем одной строкой.
- Tailwind не переносит стили примитивов в страницы: их варианты и оформление остаются в atoms, общие токены — в foundation.

Сортировка и разрешение конфликтов классов — разные задачи. См. [tailwind-merge](https://github.com/dcastil/tailwind-merge) и [Biome useSortedClasses](https://biomejs.dev/linter/rules/use-sorted-classes/javascript/). У последнего есть ограничения и статус nursery; настройку из старого проекта не копируем без проверки.

## Faker и моки

Faker — генератор данных, а не замена HTTP-мокам. Генерация живёт в mocks или изолированной инфраструктуре stories/демо, а не в production-сервисах и UI.

Fixtures должны быть воспроизводимыми: используем фиксированный seed, при работе с относительными датами — фиксированную опорную дату. Учитываем зависимость результата от версии Faker и порядка вызовов. Для независимых сценариев создаём отдельные экземпляры/фабрики, чтобы они не влияли друг на друга. [Документация Faker](https://fakerjs.dev/guide/usage.html).

Для одного короткого ответа простой объект понятнее обязательного подключения генератора.

## Актуальность версий

Новый проект начинает работу на последних стабильных версиях выбранных зависимостей. Перед установкой проверяем npm dist-tag latest и официальные release/migration notes. Не копируем версии из старого проекта по памяти; скелет в examples версий не фиксирует.

- Проверяем engines, peerDependencies и совместимость framework, сборщика, плагинов, TypeScript, Biome и Storybook. Beta, RC, next и nightly не используем без отдельной задачи.
- В package.json записываем проверенные числовые версии/диапазоны, в lock-файле — точное дерево. Не оставляем latest или * вместо воспроизводимой конфигурации. CI использует npm ci.
- Если последний стабильный релиз несовместим, явно называем пакет, ограничение и выбранную совместимую версию. Не понижаем версию молча и не скрываем конфликт через --force или --legacy-peer-deps.
- Типы среды соответствуют самой среде: @types/node выбирается для принятой major-версии Node, @types/react — для React. Для нового проекта выбираем актуальную поддерживаемую LTS Node; системный runtime существующего проекта не меняем без задачи.
- После обновления адаптируем конфиги, включая удалённые параметры TypeScript и schema Biome. Запускаем чистую установку, форматирование/lint, typecheck, сборку приложения и Storybook; при смене сборщика проверяем браузерный сценарий.
- Существующий проект обновляем в рамках задачи обновления, а не при каждом изменении бизнес-кода. Проверки безопасности и совместимости важнее механического отсутствия строк в npm outdated.

## Перед первоначальной реализацией

Агент показывает компактный выбор: framework/runtime, routing при необходимости, запросы, формы, стили, форматирование, Storybook и режим проверок. Указывает, что берёт из существующего проекта и от чего предлагает отклониться. Владелец проекта согласует набор один раз до реализации.

Уже согласованный набор действует дальше: не нужно спрашивать разрешение на каждую обычную зависимость внутри принятого решения. При существенном изменении стека или замене готового механизма собственным решение обсуждается снова.

Для существующего проекта сначала читаем его конфигурацию. Не мигрируем стек автоматически ради предпочтений этого каталога.

## Первая итерация

1. Согласовать инструменты и небольшой показательный сценарий.
2. Реализовать читаемый вертикальный пример: UI → локальная модель → DTO → сервис → ответ.
3. Проверить оформление, типы, сборку, stories и поведение в браузере доступными средствами.
4. После ревью эталона расширять приложение и согласованный набор постоянных тестов.

Проверка результата не означает автоматическое создание тестового framework и test-файлов. Обязательные тесты из задания сохраняются; дополнительные постоянные тесты в первой итерации согласуются по полезным сценариям. Storybook при этом остаётся обязательной визуальной документацией UI.
